# Root template assembly differential

`cargo test --test template_swift` replays 27 persisted observations from actual Swift execution. `python3 tools/generate-template-vectors.py` regenerates them using the existing pinned full-Lattice cache at `/tmp/lattice-genesis-oracle`. It verifies every original Lattice Swift source and the dependency lock before building. It requires sibling source repositories and the prepared cache; it makes no node requests or work submissions.

The node reference is `0xLattice/lattice-node` at `3df9e0a786c7b103a3da88d1c3881efc81706255`; Lattice is `dda2d852429a27be6043599b63bde81530cd9514`. `tests/template-swift-evidence.json` records reference source hashes and the corpus hash.

The harness compiles the complete original `MiningTemplateAssembly.swift`, removing only three unavailable module import lines (`Ivy`, `LatticeNodeCore`, `LatticeNodeAPI`). The exact original policy-selection method, digest method, transaction CID method, TemplateChain declaration, minimum-work implementation, and directory validators are extracted unchanged into its executable. The four assembly error case names and timestamp overflow case have a harness-only error declaration. The assembly runs against unchanged full Lattice/Cashew/crypto/WasmKit libraries. This is source-extracted node assembly evidence, not a build or execution of the entire Swift node. Timestamp clamping is supplied explicitly to make wall-clock-independent cases; it does not execute `MiningPlan.nextTimestamp`'s Date read.

Each successful case compares the exact block CID, work ID, search target, target ladder, mempool digest, refused transaction CIDs, and selected transaction CIDs in index order. Failure cases compare refusal to build, not error text or error precedence. Named positive cases separately assert successful construction and useful selected counts; matching failures cannot silently turn those into weaker cases.

Coverage includes empty work, floor/forward timestamps, timestamp and height overflow, supplied difficulty anchors (including an anchor after the previous height), conflict bisection, all-conflicting input, transaction count and logical byte limits, an impossible byte limit, valid/invalid reward recipients, root/descendant/multiple minimum-work policies, signed transactions, accepting/rejecting/missing policy modules, and policy refusals before unavailable state or parent receipt content.

The `materializeBodies` flag is intentional. Swift assembly checks the original transaction bodies for loaded withdrawal metadata. Any unresolved body triggers `validateWithdrawals`, which first validates all transaction signatures/basic rules. Loaded unsigned synthetic conflict transactions can be carried by this template-building API; the same unresolved transactions are excluded. These fixtures exposed the missing Rust gate and now retain both outcomes (two selected versus zero). Neither outcome grants admission authority: templates still require the normal validation path before becoming executed blocks.

Limits: this finite root-only corpus does not exercise hosted child filtering, supplied child candidates, recursive scheduling witnesses, descendant candidate rotation, HTTP plan decoding, epoch-fenced template installation, timing races, or arbitrary policy programs. Policy cases reuse the signed full-CAS preflight fixtures; they exercise actual Wasm policy execution, but the included modules do not inspect the candidate timestamp/height. Runtime tests and other differential corpora provide separate evidence for those components where present.
